# Reflection

I drew the tool boundaries around three distinct responsibilities: retrieving catalog information, persisting a reservation, and coordinating a find-and-reserve request. The Data tool reports availability without changing files, while the Action tool validates a specific book and student before writing. The Orchestration tool reuses both functions and controls the sequence. When several available books match, it returns choices rather than silently selecting one. This keeps the decision visible to the user and avoids duplicating the searching or reservation logic. Thin FastMCP wrappers keep the protocol layer separate from the ordinary Python functions, which can be tested directly.

Three tools are sufficient for this limited demonstration: the agent can answer lookup requests, reserve a known book, or complete a higher-level request. Adding cancellation, due dates, or account management would require additional tools or a larger scope. JSON persistence keeps the implementation easy to inspect, but it assumes sequential requests and one copy per book. A next step would be database-backed reservations with transaction handling if several clients needed to operate simultaneously. Testing the library rules separately from the SDK and MCP connection also makes it easier to distinguish function errors, transport errors, and model tool-selection behavior.
